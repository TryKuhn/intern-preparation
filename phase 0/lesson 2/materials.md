### Модель данных Git

Git хранит историю как граф коммитов. Каждый коммит — это снимок всех файлов плюс ссылка на родительский коммит. Объекты хранятся по SHA-хешу содержимого, поэтому одинаковые файлы не дублируются.

Три уровня хранения:
- **Рабочая директория** — обычные файлы, которые ты видишь.
- **Staging area (индекс)** — промежуточная область для следующего коммита. `git add` перемещает туда.
- **Репозиторий** — история коммитов внутри `.git/`.

**HEAD** — специальный указатель на текущую позицию. Обычно указывает на ветку, которая указывает на последний коммит. Когда делаешь `git switch main`, HEAD переключается на ветку `main`.

### Базовые команды

```bash
git init                     # создать репозиторий в текущей папке
git clone URL                # клонировать существующий репозиторий
git status                   # посмотреть текущее состояние
git add file.cpp             # добавить файл в staging
git add .                    # добавить все изменения (осторожно!)
git commit -m "сообщение"    # создать коммит
git log --oneline --graph    # краткая история с ветками
git diff                     # изменения в рабочей директории (до add)
git diff --staged            # изменения в staging (после add, до commit)
```

`.gitignore` — файл в корне репозитория. Строки в нём — паттерны файлов, которые git игнорирует. Пример:
```
*.o
*.d
build/
.DS_Store
```

### Ветки

```bash
git branch feature-login     # создать ветку
git switch feature-login     # переключиться на ветку
git checkout -b feature-login # создать и сразу переключиться (старый синтаксис)
git branch -d feature-login  # удалить ветку (после merge)
git merge feature-login      # слить ветку в текущую
```

**Merge vs rebase.** Merge создаёт merge-коммит, сохраняя оригинальную историю. Rebase переписывает коммиты поверх другой ветки — история становится линейной, но SHA-хеши меняются. Правило: `git rebase` можно делать только на своих локальных ветках, которые не опубликованы.

**Конфликты.** Когда две ветки изменили одну строку, Git не знает, какую оставить. Он добавляет маркеры в файл:
```
<<<<<<< HEAD
версия из текущей ветки
=======
версия из сливаемой ветки
>>>>>>> feature-login
```
Нужно вручную отредактировать файл, убрать маркеры, сделать `git add`, затем `git commit`.

### Удалённый репозиторий

```bash
git remote add origin https://github.com/user/repo.git
git push -u origin main      # push и запомнить upstream
git push                     # push (после -u)
git pull                     # fetch + merge (обновить локальную ветку)
git fetch                    # только скачать изменения (без merge)
```

**PR-флоу на GitHub**: создать ветку → push ветки → открыть Pull Request в интерфейсе → ревью → merge. Это стандартный способ вносить изменения в командных проектах.

### Откаты

| Команда | Что делает | Трогает историю? |
|---|---|---|
| `git restore file` | Отменить изменения в файле (до add) | Нет |
| `git restore --staged file` | Убрать из staging (после add) | Нет |
| `git reset --soft HEAD~1` | Убрать последний коммит, изменения в staging | Да (локально) |
| `git reset --mixed HEAD~1` | Убрать коммит, изменения в рабочей директории | Да (локально) |
| `git reset --hard HEAD~1` | Убрать коммит и все изменения — **необратимо** | Да (локально) |
| `git revert HEAD` | Создать новый коммит, отменяющий изменения | Нет (безопасно) |

Золотое правило: не переписывать историю коммитов, которые уже запушены и которые видят другие.
