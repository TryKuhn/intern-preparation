### A. Создать репозиторий и первые коммиты (около 30 мин)

1. Создай новую папку `git-practice`, сделай `git init`.
2. Создай файл `main.cpp` с минимальной программой `Hello, Git!`, добавь его и сделай первый коммит с осмысленным сообщением.
3. Измени программу, добавь ещё один файл `utils.cpp`. Сделай `git status` и `git diff`, объясни себе что видишь. Затем сделай второй коммит.
4. Создай `.gitignore` который игнорирует `*.o`, `*.out`, `build/`. Проверь что `touch test.o` действительно не показывается в `git status`.
5. Посмотри `git log --oneline --graph` и сохрани его вывод в `log.txt`.

### B. Ветки и конфликты (около 50 мин)

1. В репозитории из части A создай ветку `feature-greet`. Переключись на неё.
2. Измени `main.cpp` так, чтобы программа выводила приветствие с именем (аргумент командной строки).
3. Сделай коммит на `feature-greet`. Переключись обратно на `main`.
4. На ветке `main` тоже измени `main.cpp` — добавь любую другую строку.
5. Сделай `git merge feature-greet`. Разреши конфликт вручную. Сделай коммит.
6. Изучи `git log --oneline --graph` — найди merge-коммит.
7. Создай ещё одну ветку `feature-calc`. Сделай в ней коммит. Вернись в main. Выполни `git rebase feature-calc` на main (или наоборот, поэкспериментируй). Сравни граф до и после rebase.

### C. Удалённый репозиторий (около 30 мин)

1. Создай репозиторий `cpp-practice` на github.com (без автоматических файлов).
2. Подключи его как remote к локальному репозиторию: `git remote add origin URL`.
3. Сделай `git push -u origin main`.
4. Создай новую ветку `feature-readme`, добавь `README.md` с описанием проекта, запушь ветку: `git push origin feature-readme`.
5. Открой Pull Request на GitHub из `feature-readme` в `main`. Merge его через интерфейс.
6. Локально сделай `git pull` и убедись что изменения появились.

### D. Откаты (около 30 мин)

1. Сделай три коммита подряд с небольшими изменениями.
2. Отмени последний коммит через `git reset --soft HEAD~1`. Что теперь в staging?
3. Восстанови коммит (или сделай новый). Теперь отмени через `git reset --mixed HEAD~1`. Чем отличается от --soft?
4. Создай отдельную ветку для эксперимента. Там сделай коммит. Попробуй `git reset --hard HEAD~1`. Убедись что изменения исчезли.
5. На main сделай коммит с «ошибкой». Отмени его через `git revert HEAD`. Сравни с reset: почему revert безопаснее для общих веток?
6. Используй `git restore` чтобы отменить изменения в файле до `git add`. Затем `git restore --staged` после add.

### Самопроверка (около 20 мин, письменно в `selfcheck.md`)

1. Что такое HEAD? Может ли HEAD указывать не на ветку?
2. Чем `git fetch` отличается от `git pull`?
3. В каких случаях нельзя делать `git rebase`? Почему?
4. Ты случайно сделал `git add .` и добавил файл с паролями в staging. Как убрать его оттуда?
5. Объясни разницу между `merge` и `rebase` своими словами. Когда что использовать?
6. Что произойдёт если сделать `git reset --hard` на ветку, которая уже запушена?
7. Почему `git revert` создаёт новый коммит вместо того чтобы удалять старый?

### Критерий "сделано"
Репозиторий существует на GitHub, в нём есть коммиты на нескольких ветках, один разрешённый конфликт и один PR. В `selfcheck.md` ответы своими словами.
