### Четыре этапа сборки C++

```
main.cpp  →  [Препроцессор]  →  main.i  →  [Компилятор]  →  main.s  →  [Ассемблер]  →  main.o  →  [Линкер]  →  program
utils.cpp →  [Препроцессор]  →  utils.i →  [Компилятор]  →  utils.s →  [Ассемблер]  →  utils.o ↗
```

**Препроцессор** (`g++ -E`): раскрывает директивы `#include`, `#define`, `#ifdef`. Результат — один большой `.i` файл, всё ещё C++. `#include <iostream>` буквально вставляет ~40 000 строк.

**Компилятор** (`g++ -S`): текст C++ → ассемблер (`.s`). На этом этапе ловятся синтаксические ошибки и большинство ошибок типизации. Каждый `.cpp` компилируется **независимо** — компилятор не знает о существовании других файлов.

**Ассемблер** (`g++ -c`): ассемблер → машинный код в объектный файл (`.o`). В `.o` символы (имена функций) пока нерезолвленные — указатели-заглушки.

**Линкер** (`g++` без флагов, или `ld`): соединяет все `.o` файлы, находит и подставляет адреса символов. Если символ обещан (объявлен в заголовке), но не определён — ошибка «undefined reference».

### CMake

```cmake
cmake_minimum_required(VERSION 3.15)
project(MyProject)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(myapp main.cpp utils.cpp)

# Внешняя библиотека (например, fmt):
# find_package(fmt REQUIRED)
# target_link_libraries(myapp PRIVATE fmt::fmt)
```

**Out-of-source build** — сборка в отдельной папке, чтобы генерированные файлы не смешивались с исходниками:
```bash
mkdir build && cd build
cmake ..          # генерирует Makefile (или Ninja)
make -j4          # собирает параллельно на 4 ядрах
./myapp
```

### ODR — правило одного определения

Каждая функция, переменная, класс должна быть **определена** не более одного раза во всей программе. Объявлений может быть много.

```cpp
// header.h — определение функции в заголовке = ошибка ODR при включении в несколько .cpp
void foo() { ... }  // ОШИБКА: multiple definition если header.h включён в 2 файла

// Правильно:
// header.h
void foo();         // только объявление

// utils.cpp
void foo() { ... }  // одно определение
```

### Header guards и `#pragma once`

```cpp
// Вариант 1: header guard (классика)
#ifndef MY_HEADER_H
#define MY_HEADER_H
// содержимое
#endif

// Вариант 2: pragma once (современный, рекомендуемый)
#pragma once
// содержимое
```

Оба предотвращают двойное включение одного заголовка.

### `inline` и статические переменные в заголовках

```cpp
// Без inline — ODR-нарушение при включении в несколько .cpp:
int counter = 0;        // ОШИБКА в заголовке

// С inline — разрешено (C++17 для переменных):
inline int counter = 0; // OK в заголовке

// Функции в заголовках всегда нужно помечать inline:
inline int square(int x) { return x * x; }
```

`inline` — это разрешение компоновщику принять несколько одинаковых определений (он выберет одно). Это **не** гарантия встраивания в код.

### `static` = внутренняя линковка

```cpp
// utils.cpp
static void helper() { ... }  // видна только внутри utils.cpp
static int internal_counter;   // аналогично
```

Эквивалент `private` на уровне единицы трансляции. Используется для скрытия деталей реализации.

### Форвард-декларации и неполные типы

```cpp
// Вместо #include "BigClass.h" можно написать:
class BigClass;            // форвард-декларация — неполный тип

void process(BigClass* p); // указатель на неполный тип — OK
// void process(BigClass b);  // ОШИБКА — нужен полный тип
```

Уменьшает зависимости между заголовками и ускоряет компиляцию.

### Отладка с gdb

```bash
g++ -g -O0 program.cpp -o program   # -g: отладочная инфо, -O0: без оптимизаций
gdb ./program
(gdb) break main          # точка останова
(gdb) run                 # запустить
(gdb) next                # шаг (без захода в функцию)
(gdb) step                # шаг с заходом в функцию
(gdb) print x             # напечатать переменную
(gdb) backtrace           # стек вызовов
(gdb) quit
```
