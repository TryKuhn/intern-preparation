0–5 мин. Зачем это всё.
Обсуди вопрос: программа на C++ — это текст. Чтобы процессор её выполнил, нужно пройти несколько этапов. Разработчик должен понимать эти этапы, иначе ошибки линкера будут казаться магией. На стажировках часто спрашивают этапы компиляции.

5–30 мин. Четыре этапа сборки.
Покажи вживую, что происходит с файлом `hello.cpp`:
```
g++ -E hello.cpp -o hello.i   # 1. Препроцессор
g++ -S hello.i -o hello.s     # 2. Компиляция → asm
g++ -c hello.s -o hello.o     # 3. Ассемблирование → объектный файл
g++ hello.o -o hello          # 4. Линковка → исполняемый
```
Открой `hello.i` — покажи раздутый вывод после `#include`. Открой `hello.s` — покажи, что это ассемблер. Открой `hello.o` через `xxd hello.o | head` — покажи, что это бинарник.
- **Препроцессор**: раскрывает `#include`, `#define`, `#ifdef`. Его вывод — всё ещё C++.
- **Компиляция**: текст C++ → машинный код / asm. Каждый `.cpp` компилируется независимо.
- **Линковка**: склеивает объектные файлы, разрешает символы (имена функций). Здесь возникают ошибки «undefined reference».
Вопрос: если я добавлю новый `.cpp` — нужно ли перекомпилировать остальные? (Нет, только этот, потом линкуем.)

30–50 мин. Базовый CMake и gdb.
Создайте вместе проект с двумя файлами:
```cmake
cmake_minimum_required(VERSION 3.15)
project(MyProject)
set(CMAKE_CXX_STANDARD 17)
add_executable(myapp main.cpp utils.cpp)
```
```bash
mkdir build && cd build
cmake ..
make
./myapp
```
Покажи: CMake генерирует Makefile (или Ninja), реальная сборка делается через make. Это out-of-source build — исходники не загрязняются.

gdb — кратко: `g++ -g hello.cpp -o hello`, `gdb ./hello`, `break main`, `run`, `next`, `print x`, `quit`. Флаг `-g` добавляет отладочную информацию.

50–70 мин. Ошибки компилятора и линкера.
Разберите несколько сценариев:
1. Ошибка компилятора: опечатка в имени переменной — читай первую строку, игнорируй лавину.
2. Ошибка линкера «undefined reference to `foo()`»: функция объявлена в заголовке, но определения нет. Добавить `.cpp` в CMake.
3. Ошибка линкера «multiple definition of `foo`»: нарушение ODR.

70–85 мин. ODR, header guards, inline, static.
- **ODR** (One Definition Rule): каждая функция/переменная должна быть определена ровно один раз во всей программе. Это объясняет, почему функции нельзя определять в `.h` файлах без `inline`.
- **Header guards vs `#pragma once`**: оба решают проблему двойного включения. `#pragma once` — де-факто стандарт, поддерживается всеми компиляторами.
- **`inline`**: разрешает множественные одинаковые определения (например, в заголовке). Не гарантирует встраивание — это подсказка. С C++17: inline-переменные (`inline int x = 42;` в .h).
- **`static` на уровне файла**: внутренняя линковка — символ не виден из других `.cpp`. Скажи ей: это как `private`, но для целого файла.
Подводный камень: включить `.cpp` вместо `.h` — классическая ошибка новичков, сломает ODR.
